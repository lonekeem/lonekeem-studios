# After the Quiet — Multiplayer ("Survival", Beta) architecture plan

Status: **Phase 1** (this branch `feat/multiplayer`). Story mode is untouched; everything lives in `src/mp/` and is reached from the main menu via **Multiplayer (Beta)**.
Owner's saved roadmap is summarised in §1; what is built vs planned is in §14.

---

## 0. Design principles (from Keem)

1. **Everything realistic.** Environments, lighting and weather, survival mechanics, car handling and fuel, NPC and zombie behaviour and animation must all be believable and physically grounded. *Characters* stay in the smooth stylised cartoon 3D look (same style as the Keem model); the *world and rules* are realistic.
2. **Original assets only.** No brand logos or names anywhere (guns, cars, clothes, packaging). Cars wear an original **"KL" emblem** instead of a manufacturer badge. No Bitmoji / Snapchat assets. Models are CC0 or generated by us (Fal/Meshy base bodies, procedural geometry).
3. **Phones first.** Every system has a budget (§11). If it cannot hold ~30 fps on a mid-range Android phone it is cut down, streamed, or faded.
4. **No teleporting.** Zombies, NPCs and cars always arrive from somewhere physical (see §9).
5. **Server authoritative where it matters** (money, items, house ownership, zombies); client authoritative only for its own movement, with sanity checks.
6. **Player characters have no voice** (no voice lines or voice customisation).
7. **Nothing costs money without approval.** Phase 1 uses no paid service. Supabase use below is on the *existing* project and free tier only; the project is currently `INACTIVE` (paused) and must be restored by the owner before any server work (see §3).

## 2. Layers

```
┌────────────────────────────────────────────────────────────────────────────┐
│ Client (browser / Capacitor Android)           src/mp/*                    │
│  creator.js  UI + live 3D preview     avatar.js  body + shells + animation │
│  catalog.js  item data model          look.js    look JSON (save format)   │
│  lobby.js    free-roam test world     net.js     transport adapter         │
├────────────────────────────────────────────────────────────────────────────┤
│ Transport adapter (net.js)                                                 │
│   Phase 1: BroadcastChannel (same browser, 2 tabs) – zero cost             │
│   Phase 2: Supabase Realtime (presence + broadcast) – free tier            │
│   Phase 3: dedicated authoritative game server (Node/uWebSockets, zombies) │
├────────────────────────────────────────────────────────────────────────────┤
│ Persistence: Supabase Postgres (schema `atq_mp`) + Auth + RLS              │
└────────────────────────────────────────────────────────────────────────────┘
```

* **Accounts**: Supabase Auth (email magic link / Google; anonymous sign-in for beta, upgradeable). The same `user_id` keys every table. Row-level security: a user can read/write only their own rows; public read of `characters.look` for rendering other players.
* **Saves**: `atq_mp.characters` (look JSON), `atq_mp.wallets` (diamonds, stars, cash), `atq_mp.inventories`, `atq_mp.houses`, `atq_mp.house_items`, `atq_mp.vehicles`. SQL draft: `supabase/migrations/20261118_mp_phase1.sql` (not applied).
* **Realtime presence/lobby**: one Realtime channel per *shard* (`world:{shard}`); players broadcast `pos` at 10 Hz (quantised, delta-compressed); presence tracks name, look hash, vehicle id.
* **Why not Realtime for zombies**: Supabase Realtime is fan-out of messages, not a simulation. Zombies, cars, doors and loot need one authoritative simulator per shard → Phase 3 game server (a small Node process; ~$5/mo class VPS — **needs owner approval**). Until then the lobby is peer-to-peer presence only.

Non-admins get the same slots minus the Original Keem option. Other players still *render* the admin's Keem look (characters stay publicly readable), only *choosing* it is locked. Offline / BroadcastChannel test mode has no accounts, so the creator treats the local player as a non-admin unless `?admin=1` is set in dev builds (dev convenience only; the server is the real gate).

## 4. Character look (the save format)

A look is a small JSON document (≈1–3 KB), versioned, so catalog growth never breaks old saves:

```jsonc
{ "v": 1, "name": "Keem", "base": "mp_m1",              // male/female body mesh
  "skin": { "t": 0.72, "under": 0.1 },                   // 0 light … 1 deep + undertone, fine slider
  "morph": { "jaw": 0.2, "noseW": -0.3, "muscle": 0.4 }, // −1..1 sliders (head + body)
  "face": { "eyeShape": 1, "eyeSize": .5, "eyeColor": "#4a2c17", "brow": 2, "mouth": … },
  "hair": { "id": "hair.fade_curls", "c1": "#150d08", "c2": "#3a2a1a", "len": .5 },
  "beard": { "id": "beard.goatee", "len": .4, "dens": .9, "c1": "#150d08" },
  "marks": { "freckles": .3, "scar": 2, "tattoo": 1 }, "makeup": { … },
  "gear": { "top": {"id":"top.hoodie","c1":"#223","p":4,"c2":"#999","fit":2,"sleeve":4}, "pants": {…},
            "shoes": {…}, "hat": {…}, "glasses": {…}, "earL": {…}, "chain": {…} } }
```

* `"exclusive"` (optional string): whole-character exclusive skin id, e.g. `skin.keem_story` (admin only, enforced by RLS, see §3). Absent for normal looks.
* Items are referenced by **string id + parameters**, never by index, so ids are stable forever. Unknown ids are ignored (forward compatible).
* A look renders identically on every client because everything is deterministic (analytic shaders + parameters). Remote players only need the JSON.

## 5. Catalog scaling (clothes / hair / jewellery → 1000+ choices)

Choice count = **families × named styles × cut variants × colours × patterns**. Authoring cost grows with the first two only:

| Layer | What it is | Authoring cost |
|---|---|---|
| Family | Geometry builder or shader rule set (e.g. `hat.brimmed`, `top.cut`) | code |
| Named style | A parameter preset of a family ("Fedora", "Cowboy") — a catalog row | one line of data |
| Cut variants | Sleeve / hem / neckline / fit (tops), brim / crown (hats), length (hair)… | slider/chip |
| Colour | 2–3 colour slots, swatch palette + free picker | none |
| Pattern | 16 fabric patterns (stripes, plaid, camo, polka, …) | none |

`catalog.js` exports `COUNTS` computed from the data, and the creator header shows it ("Named styles: N · distinct cuts: M · with colours & patterns: K"). Numbers in the UI are always computed, never typed in.
UI scales via category tabs → search box → filter chips (style tag, gender) → virtualised scrolling grid → ♥ favourites (stored in the look profile) → recently used row.

## 6. Creator (Phase 1, built)

* Live 3D preview: orbit by dragging, pinch/scroll zoom, camera presets (full / face / hands / shoes), idle animation, walk preview.
* Tabs: **Body** (type male/female base mesh, skin tone + fine slider + undertone, height, build sliders) · **Face** (head/jaw/chin/cheek/forehead, eyes shape/size/spacing/colour, brows, nose, lips, ears) · **Hair** · **Beard & stache** · **Skin details** (freckles, scars, moles, tattoos, makeup, age) · **Clothes** (tops, jackets, pants, shoes, gloves) · **Head gear** (hats, glasses, masks) · **Jewellery** (earrings, piercings, necklaces, rings, bracelets, watches) · **Bags** · **Randomize / Reset / Save**.
* Rendering technique (important for phones): one skinned body mesh, **no textures**. Skin and the whole painted face are analytic shaders; garments are shells of the same mesh offset a few millimetres and cut analytically (sleeve/hem/neck/waist) — so a new garment is a parameter set, not a model. Hair/beards are shells + a few merged primitive meshes. Typical avatar ≈ 8–14 draw calls, ~25 k triangles.

## 7. Vehicles ("real-world look, KL emblem")

* Visual: CC0 car kit (Kenney, in repo) now; later original or CC0 higher-detail bodies in real-world body styles (hatch, sedan, SUV, pickup, van, coupe, off-road). **No brand names, grilles or logos copied**; every body carries a **KL emblem** (disc badge with "KL") on grille/boot/steering wheel/wheel caps. The emblem is a shared texture/decal slot, so changing it is one asset.
* Customisation (data-driven like clothes): paint (colour + finish + pattern), wheels, armour plates, push bar/plow, roof cage, window bars, spikes, lights, horn, decals. Each part: `{id, slot, price, mass, armor, drag}`.
* Handling: arcade-realistic rigid-body model — per-wheel suspension raycasts, tyre friction curve (slip angle), weight transfer, engine torque curve + gearbox, brakes/handbrake, mass changes from armour. Server validates speed (anti-teleport) and resolves car-vs-zombie collisions.
* **Fuel**: tank size per body, consumption = f(throttle, rpm, mass, speed); stalls at 0; refuel from jerry cans/pumps (pumps need power or siphoning). Gas, wood, scrap etc. are scavenged world resources (§10).
* **Break-in + hotwire**: locked cars need lock-pick/crowbar/smashing a window (noise → attracts zombies). Hotwire mini-game: pick wires in order with timing; fails raise noise and can shock. Keys/ignition owned cars skip it.
* Phase 1: one drivable test car with KL badge in the lobby (arcade model).

## 8. Houses, cabins and fortification

* **Ownership**: `houses` table, one row per placeable plot (id, chunk, door anchor, tier, price). `buy_house` RPC debits wallet atomically and sets `owner_id` permanently. Cabins are houses in forest chunks.
* **Customisation catalog (~1000 items)**: furniture, decor, wall finishes, floor finishes, lights, appliances, storage, fortifications. Same data model as clothes: family × style × colour × material, e.g. `{id:"sofa.2seat", style:"modern", c1:"#…", mat:"leather"}`.
* **Placement save format** (`house_items`): `{house_id, item_id, params jsonb, pos [x,y,z] (cm int), rot_y (1/256 turn), scale, room}` → ≤ 40 bytes/item; a house holds ≤ 400 items (budget). Loaded as one row set per house, instanced by item family.
* **Break-in and fortification**: every opening (door, window, wall segment, fence) is a **structure piece** with `hp`, `armor_class` and a `tier`. Zombies attack the weakest reachable piece on their path (noise/light/scent pull them); damage = Σ zombies × dps vs piece hp (+ repair rate). Tiers: 0 wood/plain glass → 1 boarded/barricaded → 2 reinforced door, window bars → 3 steel door/shutters, fences, spiked barricades → 4 concrete/electric fence, turrets. Traps (spikes, noise cans, tripwire, bear trap, flame), alarms and lights are items that trigger on zombie contact. Pieces are repaired with materials. State (hp, tier) persists in `house_pieces`.
* Offline (owner logged out): the house simulation is **abstracted** — raids resolve as an expected-damage calculation when someone loads the chunk or on a coarse timer, never as full simulation.

## 9. Zombies, NPCs and events (server-side)

**Never-ending without teleporting** — zombies are *spawned off-screen and walk in*:

* World is divided into chunks (§12). Each simulated chunk has a **horde budget** `B(chunk) = base(density) × time-of-day × (1 + noise generated by players) ` capped globally per shard (e.g. 120 active zombies/shard, 40 per player).
* Spawn points are **physical places**: forest edges, road ends, building doors/alleys, graveyards, cars, rubble. A spawn is only allowed when the point is **outside every player's view frustum and ≥ 60 m away** (line-of-sight checked on a coarse grid), otherwise it is deferred. Zombies then path (flow-field on a navgrid) toward the nearest stimulus: players, noise events, light, vehicles.
* **Always chasing**: stimuli (sight 30 m, hearing by noise radius, scent trail) feed a per-zombie target; a *threat map* per player is updated at 2 Hz. Zombies keep the chase while the player drives (they are outrun and drop off), and gather around houses. Idle zombies wander/shamble between places so the world never looks empty.
* **LOD of simulation**: near (≤ 40 m) full steering + animation at 30 Hz; mid (40–120 m) simplified steering at 5 Hz, no ragdoll; far: **abstracted** crowd cells (count + heading) that re-materialise as individuals when a player comes within range (always from the cell edge facing the player → no pop-in).
* **NPCs/town events**: an *event director* picks randomised scenarios per chunk (cooldown + weight by danger and day/night): survivor flees a pair of zombies, one gets caught and eaten (corpse persists), one escapes into a house/car, a looter fights back, a convoy crash, a horde passes through, a distress signal. NPCs run the same steering as zombies with a *flee/hide/fight* state machine and are consumed by the same body system.
* **Horde events**: scheduled big waves on towns; announced on the radio; everyone near defends fortified positions.
* Zombie health/damage/stagger and feeding animations reuse story-mode assets; multiplayer sends only `{id, type, x, z, heading, state, hp-bucket}` quantised to ~10 bytes.

## 10. Survival systems (all must be realistic)

Day/night cycle (zombies faster/more alert at night) · hunger, thirst, sleep and temperature · crafting (junk → weapons, traps, bandages, barricades, fuel) · weather (rain/fog/storm affecting visibility, hearing, traction, fire) · noise (gunshots, alarms, engines pull zombies) · crews (shared bases, friendly-fire rules, shared storage) · pets (dog that follows and warns) · infection (bite → timer → cure or turn) · radio and safe zones (traders/missions) · horde events. Looting: containers with weighted loot tables per building/vehicle type; items are stackable ids; weights and capacity limit carrying.

## 11. Performance budgets (mid-range phone)

| Item | Budget |
|---|---|
| Frame | 33 ms (30 fps), CPU main thread ≤ 14 ms |
| Draw calls | ≤ 250 total; player avatar ≤ 14; remote avatars share materials, **LOD to impostor/low avatar beyond 25 m** |
| Triangles on screen | ≤ 350 k |
| Active zombies rendered | ≤ 40 (instanced, 3 LOD levels); more are abstracted |
| Dynamic lights | 1 sun/moon + ≤ 4 local (cars, flashlights) |
| Shadows | one cascade (≤ 40 m) on high; off on low |
| Network | ≤ 12 KB/s down, ≤ 3 KB/s up per client |
| Memory | ≤ 700 MB; chunks beyond ring 2 unloaded |
| Avatar texture memory | **0** (analytic shaders) |

Quality auto-scales (render scale, shadow, view distance, zombie cap, avatar LOD) from a 3-second GPU timing probe at start.

## 12. Huge map: chunking and streaming

* World = 128 m × 128 m chunks (grid in a single coordinate system, 20 km × 20 km target). Chunk file (`chunks/{x}_{z}.bin`): terrain heightmap tile (e.g. 65×65 16-bit), splat map, water mask, road splines, prop/instance lists (trees, rocks, buildings by id, transform), spawn points, nav data, house plots, loot nodes. Authored in a generator (`tools/mapgen`) + hand-placed landmarks.
* Streaming: load ring 0–2 (≈ 3 × 3 … 5 × 5 chunks) by distance, decode in a Web Worker, upload geometry across frames (≤ 2 ms/frame). Far terrain uses a coarse low-res mesh + fog; far props are impostors/billboards. While driving, prefetch along the heading.
* Biomes: town grid, suburbs, farmland, **forest** (instanced trees with wind, undergrowth), **lakes/rivers** (flow-aligned animated water shader with depth colour, shore foam, reflections cube-mapped; shallow = wade slowly, deep = swim/drown, cars sink), **bridges** (collidable decks with railings, can be blocked by wrecks).
* Props use **instancing** (`InstancedMesh`) keyed by model id; buildings by kit pieces; interiors loaded only when a door is opened/entered.
* Collision: heightfield + static AABB/capsule grid per chunk; no per-triangle physics on the client.
* Bodies: see §13.

## 13. Persistent bodies (performance-safe)

* Every dead zombie/NPC/player creates a **corpse record** `{id, chunk, pose-id, x, z, heading, type, look-hash, died_at}` (≈ 16 bytes). Records persist (server memory + periodic snapshot to DB) with a **per-chunk cap** (e.g. 60). When the cap is exceeded, the oldest *off-screen, ≥ 80 m away* corpses are merged into **decals/bone piles** (a single blood-stain + skeleton decal per cluster) rather than deleted, so the world still looks lived-in.
* Rendering: corpses are **frozen poses** (no skeleton update), drawn via `InstancedMesh` per type with baked pose; within 12 m full avatar mesh, beyond that LOD. Fade/merge happens only when not visible (outside the frustum or behind the occlusion distance) so players never see them vanish.
* Players' own corpses keep their dropped loot (timed), and their look is hashed so the corpse matches who died.

## 14. Weapons store (~1000 guns)

Data model: `gun = receiver family × barrel × stock × grip × optic/mag slots × finish × tune`. A **base model** (procedural builder per family: pistol, revolver, SMG, rifle, DMR, shotgun, sniper, LMG, launcher, melee) + parameter set yields named guns; stats = base × part modifiers; price = f(stats). ~60 base models × part combos × finishes ≫ 1000 purchasable variants, each with a unique generated name and **no real brand names/logos** (item names are original). Store UI reuses the creator catalog UI (tabs, search, favourites). Prices in cash / diamonds; unlocks gated by stars.

## 15. Missions, currencies, Google Play Billing

* Currencies: **cash** (soft, earned), **stars** (progression/unlocks), **diamonds** (premium, also earned from missions). Missions defined in data (`{id, objective, region, reward:{diamonds,stars,cash}}`), progress server-side, claim via RPC.
* **Google Play Billing**: Play version only; Capacitor plugin → Play Billing Library; purchase token verified server-side with the Google Play Developer API before crediting diamonds (`purchases` table, idempotent on token). Web build has no real-money store. Needs Play Console app + service account (owner action).

Anti-abuse: guests own their row through a device secret (only its sha256 is stored), one submit / 15 s, 60 / hour, at most 60 new players / minute, caps (wave ≤ 300, kills ≤ 30 + 40·wave, kills ≤ 10 + 4·seconds, wave ≤ 1 + seconds/8, headshots ≤ kills), names stripped to letters/digits/space/_.- (16 chars). Only Survival runs count; they are sent when you die or quit (and retried later if offline). Counting happens in `trackGame()` (wraps `loadStep`/`killZ`/`onDeath`), no `game.js` edits.

Newest save wins (rev check); pushes after every profile save and whenever the title screen comes back. Local interface = fix/customize's `src/mp/profile.js` (`getProfile/saveProfile/hasProfile/onProfileChange/registerProfileSync({pull,push})`), picked up via `import.meta.glob`; a compatible fallback on the same storage keys is used until that branch is merged.
